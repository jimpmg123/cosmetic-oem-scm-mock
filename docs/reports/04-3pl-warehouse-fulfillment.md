## 한눈 요약 (TL;DR)

1. **3PL = 창고를 사거나 짓지 않고 빌려 쓰는 변동비 방식.** 물량 검증 전 단계의 정석.
2. **3PL은 입고 시 스캔/실측으로 세서 입고 전표(入库单)를 만들고**, 이를 **포털 / API 연동 / 대사 명세서 / 수동** 중 하나로 알려준다. → 우리 시스템의 **"C received"** 가 여기서 온다.
3. **B→C 운송은 물류회사가 하고**, 그 운송을 **수배·책임지는 주체(B 직납 / A 수배 / C 집화)** 는 상거래로 정한다.
4. **우리 시스템은 C를 "끼워 넣는 인터페이스"로 설계**해, 3PL이 바뀌어도 같은 출하 데이터로 대사되게 한다.

## 1. 중국 3PL 유형 (어디에 맡기나)

| 구분 | 대표 | 성격 | 우리 C 적합도 |
|------|------|------|----------------|
| **A. 대형 통합 물류** | 차이냐오 · 징둥물류 · 순펑 | 플랫폼 인프라급. 티몰·징둥 중심이면 무난 | 채널 종속 강함 |
| **B. 독립 클라우드 창고** | 파왕 등 | 재고 소유권은 브랜드가 쥐고 보관·대신 발송만 위탁 | ✅ 우리 대사 모델과 잘 맞음 |
| **C. 화장품 대행운영(代运营)** | 리런리좡 등 | 운영·마케팅·CS·물류까지 통째 위탁 | 넘기는 범위에 따라 C가 달라짐 |

> 채널이 물류를 좌우하는 배경은 [`03`](./03-china-ecommerce-logistics.md) 참조. **위챗 사적 트래픽 중심이면 B 유형(독립 클라우드 창고)을 자유롭게 선택**할 수 있어 우리 시스템과 가장 잘 맞는다.

## 2. 3PL이 입고 개수를 세서 알려주는 방식 ★

### 2.1 세는 과정 (입고, 入库)

1. **입고 예고(预约入库 / ASN)** — A 또는 B가 "○개 출하 예정"을 미리 통보
2. **도착 → 검수·카운트** — 창고가 박스/단품 **바코드·QR 스캔** 또는 실측, 예고 수량과 대조
3. **입고 전표(入库单) 생성** — **실제 수령 수량 + 차이(부족·파손·초과)** 기록
4. **통지** — 이 입고 전표가 우리 시스템의 **C received**

### 2.2 알려주는 채널 (4가지)

| 방식 | 설명 | 우리 시스템 처리 |
|------|------|------------------|
| **① WMS 고객 포털** | 3PL이 준 로그인으로 재고·입고 전표 직접 조회 | 사람이 보고 입력 |
| **② API/EDI 자동 연동** ★ | 3PL WMS가 우리 OMS/시스템에 입고 전표 자동 전송 | **자동 대사** (권장) |
| **③ 정기 대사 명세서(对账单)** | 일/주 단위 입고 명세를 엑셀·CSV로 | 파일 임포트 |
| **④ 수동 통보** | 위챗·메일로 "○개 입고" | 소규모, 불안정 |

> 알리바바 생태계에선 OMS↔WMS 연동에 **奇门(치먼)** 표준을 많이 쓴다. 중간 OMS로는 **聚水潭(쥐수이탄)·旺店通(왕뎬퉁)** 이 흔하다. **②(API 연동)** 로 가면 사람이 세지 않아도 "B 출하 vs C 입고"가 자동 대사된다 (= 02 문서 **5.E** 결정).

## 3. B→C 운송은 누가 책임지나

**"실제 운송"과 "운송을 수배·책임지는 주체"는 다르다.**

- **실제 운송** = 거의 항상 **물류회사**(택배·간선물류). 顺丰(순펑)·德邦(더방) 등 干线物流(간선 물류)가 옮긴다. B 공장이나 C 창고가 직접 트럭을 모는 게 아니다.
- **수배·책임 주체** = 상거래 합의로 정함:

| 옵션 | 누가 보내나 | 흔한 경우 |
|------|-------------|-----------|
| **A. 공장(B) 창고 직납(送货到仓)** | B가 물류사 잡아 C까지 | 공장이 "창고 배송" 서비스 제공 시 |
| **B. 우리(A)가 물류 수배** | Applicell이 물류사에 의뢰, B 픽업→C | 운송사·비용을 통제하려 할 때 |
| **C. 창고(C/3PL) 공장 집화(到厂提货)** | 3PL이 공장에서 픽업 | 3PL이 집화 서비스 제공 시 |

> 운송 주체가 중요한 이유는 **이송 중 손실·파손 책임**을 가르기 때문이다 (= 02 문서 **2.4**). 시스템에서는 **B의 출하 주장(shipment claim)** 에 운송장 번호·운송사를 함께 기록하고, **B 출하 수 vs C 입고 수 = B↔C 대사**로 이송 손실을 드러낸다.

## 4. 화장품 특수 고려

| 항목 | 내용 |
|------|------|
| **효기·배치 관리** | 效期(효기)·批次(배치) 추적 + **FEFO(선효기 선출고)** 필수 |
| **세트·샘플** | 세트 합포장·샘플 동봉 등 부가 서비스(增值服务) 빈번 |
| **보관 환경** | 온습도 관리, 일부 품목 위험물 취급 |
| **규제** | 중국 내 판매는 国家药品监督管理局(국가약품감독관리국) **신고·등록**(普通화장품 신고 등)이 선행 — **브랜드 책임**, 3PL 업무 아님 |

→ 화장품 경험 있는 클라우드 창고를 고르는 것이 안전.

## 5. 우리 시스템(C) 연동 설계 함의

```
판매 채널(티몰/더우인/위챗) ─┐
                              ├→ OMS(쥐수이탄/왕뎬퉁) → 3PL 창고(C) WMS
                              │       │                      │ 입고 전표(入库单)
                              └───────┘                      ▼
                                                   우리 추적 시스템: C received → B↔C 대사 → 최종 수율
```

1. **C는 "끼워 넣는 인터페이스"로** — 입고 수량 입력원을 ①수동 ②API ③파일 중 무엇으로든 받게 추상화. 3PL이 바뀌어도 대사 로직은 그대로.
2. **단일 창고 + 멀티채널 전제** — 여러 채널 주문이 OMS로 모여 한 창고로 가므로, C는 단일 채널을 가정하지 않는다.
3. **개발 단계** — `02` 문서의 **2단계 분리**대로, A→B와 "B 출하 주장"까지는 지금, **C 입고·대사 연동은 3PL/채널 확정 후** 설계.

## 6. 3PL 선정 체크리스트 (도입 시)

| 기준 | 확인할 것 |
|------|-----------|
| **채널 적합성** | 우리 판매 채널(티몰/더우인/위챗)과 연동·시효 충족 가능? |
| **품류 전문성** | 화장품 효기·배치·세트·샘플 처리 경험? |
| **시스템 연동** | API/치먼 연동 가능? 어떤 OMS와 붙나? |
| **분창(分仓)** | 고객 분포에 맞춘 다지역 창고로 배송 단축 가능? |
| **비용 구조** | 보관료(仓储费)·처리비(操作费)·부자재(耗材)·부가 서비스·최저 소비 |
| **규모 적합** | 우리 물량 구간을 다루는 업체인가 |

> 비용은 보통 **보관료 + 입출고 처리비(건·개수) + 부자재 + 택배비(실비) + 부가 서비스**로 쪼개진다. "월 최저 소비"가 있는 곳도 많다.
